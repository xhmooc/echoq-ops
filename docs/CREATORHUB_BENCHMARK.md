> 对标对象：`3441293738/creatorhub`（截至 2026-11-07：2937 stars / 557 forks / 20 open issues，Python + FastAPI + SQLite + Playwright/Patchright）。

## 2. CreatorHub 账号管理拆解

### 2.1 账号模型：把“登录账号”和“监控目标”分开

- 平台账号是执行任务的登录态；监控目标是你要观察的创作者或关键词，两者不是一回事。
- 顶部先选平台，再进“平台账号”；不同平台的账号、数据完全分开。
- 账号列表只回答三个问题：昵称对不对、状态正不正常、能不能被任务选中。

**对我们的启示**：我们的账号页已经按平台区分，但账号详情信息偏少，缺少“这个号现在能做什么、为什么不能做”的一屏诊断。

### 2.2 登录态：一个账号一个独立浏览器 Profile

- 每个账号有独立浏览器 Profile，Cookie、缓存、localStorage 不共享，和个人日常 Chrome 分开。
- Profile 有跨进程占用保护，避免两个进程同时打开同一份登录态。
- 小红书把登录拆成两种用途：**主站读取态**（扫码）和**创作者发布态**（创作者登录），并明确提示“能查看笔记 ≠ 能发布”。
- 登录失效时从账号列表重新登录，不删除整个数据目录。

**对我们的启示**：
- 我们的登录态以加密 Cookie / `storage_state` 注入为主（[browser.py](file:///d:/Projects/EchoQ-Ops/ops/platforms/browser.py)），没有独立持久 Profile，多开和调试时更容易互相踩状态。
- 小红书的“读取态 / 发布态”我们底层已有（PC 与 Creator 两套 API），但产品上没有显式区分，用户容易误判。

### 2.3 账号环境：代理池 + 出口基线

- 代理池支持 HTTP / HTTPS / SOCKS5 与账号密码认证。
- “测试代理”会记录出口 IP、国家、ASN、时区；账号绑定代理后保持稳定出口。
- 写任务前若出口变化或基线过期，会等待重新验证；同出口多账号集中触发风险时，进入出口组熔断。
- 代理连接失败直接报错，**不会静默改用直连**。
- 浏览器内核可选：系统 Chrome/CDP 优先，Patchright 兜底，非小红书账号可选 Fingerprint Chromium。

**对我们的启示**：我们有账号级 `proxy` 字段，但没有代理池、出口记录、出口校验与熔断。做矩阵时这是账号批量失效的主要来源之一。

### 2.4 风控调度：不是“限速”，是统一写预算

CreatorHub 的默认风控（`risk_control.mode: conservative`）有几条设计值得直接抄思路：

1. 同账号的**评论、私信、关注、发布共享写间隔与额度**，不是每个功能各自限速。
2. 同一网络出口的账号**串行访问**，未配代理的账号归入 `direct` 出口组。
3. 轻读取和重读取分开计时，避免“读一次详情”把写预算吃掉。
4. 命中 `403 / 429 / 461 / 471`、验证码或明确风险提示后，按阶梯冷却。
5. 冷却结束先做轻量探测，连续成功后再逐级恢复，不是到点直接放开。
6. 活跃时段外、限额、冷却中的任务保留为“等待”，**服务重启后继续恢复**。
7. 手动“立即执行”同样走检查，不能绕过风控。

风控中心展示：触发原因、冷却截止、恢复进度、任务级受阻原因、出口、事件时间线；规则修改、人工解除、人工探测都留审计记录。

**对我们的启示**：我们目前是账号级 `daily_limit` + `min_interval_sec` + 抖动 + 轮换（[accounts.py](file:///d:/Projects/EchoQ-Ops/ops/accounts.py)），够用但不够“可解释”。用户看到“没发出去”时，不知道是限额、间隔、账号失效还是平台拒绝。

### 2.5 账号健康与通知

- 账号状态可检测、资料可刷新；登录失效有明确提示。
- “本账号管理”里可开启**作品健康监控**：零播放、违规、下架等事件提醒。
- 通知渠道统一为 Bark / 钉钉机器人 / Telegram，全局共用，支持发送测试通知。

**对我们的启示**：我们只有账号登录态巡检，没有“发出去之后作品是否正常”的监控，也没有任何站外通知。这是发布后管理最大的空白。

### 2.6 数据与备份

- 本地 SQLite；备份包含 Profile、Cookie、数据库、私信和通知密钥，文档明确提示敏感性与换机后可能需重新登录。
- 不把 `config.yaml`、数据库、Profile 打包进公开站点。

**对我们的启示**：我们文档写了数据目录和密钥分离（[ARCHITECTURE.md](file:///d:/Projects/EchoQ-Ops/docs/ARCHITECTURE.md)），但没有应用内的备份/恢复入口。

## 3. CreatorHub 作品发布后管理拆解

### 3.1 发布结果三态：成功 / 失败 / 结果待确认

- 提交后到“发布记录”和“任务队列”观察进度。
- **任务提交成功 ≠ 平台审核通过 ≠ 公开可见**，文档反复强调要到平台侧核对。
- 连接中断或缺少成功证据时标记“结果待确认”，**不自动重试、不重复提交**，先去平台确认。
- 定时任务依赖本地服务运行，明确不是云端托管承诺。

**对我们的启示**：我们的任务状态是 `pending / retry / running / success / failed / cancelled`，没有“结果待确认”。发布过程中断时，要么重试造成重复发布，要么直接失败但平台其实已发出。这是最该补的一个状态。

### 3.2 本账号管理：作品 / 关注 / 粉丝 / 私信

- 选择账号后同步作品、关注、粉丝、私信，按平台能力差异展示。
- 作品数据按所选账号统计；没有数据就空列表，不伪造 0。
- 抖音有私信工作区，支持回复已有会话、按抖音号/主页/`sec_uid` 发起新私信；状态不确定时保留待确认，不自动重发。
- 小红书私信自动回复：关键词、排除词、模板、冷却时间、消息最大年龄；默认生成待审核草稿；首次启用只建立游标，不处理历史积压。

**对我们的启示**：
- 作品同步我们已经做了（[published.py](file:///d:/Projects/EchoQ-Ops/ops/published.py)），但只有作品，没有评论、粉丝、关注。
- 私信、自动回复、自动评论**不建议学**：与“原创内容生产”定位无关，且平台规则风险高。

### 3.3 作品健康与数据

- 零播放、违规、下架可提醒；数据与评论在本账号管理内查看。
- 数据读取失败不清空已有快照（失败保留上次结果）。

**对我们的启示**：我们 `published_notes` 的指标字段允许 NULL，区分“0 阅读”和“平台没给”（[db.py](file:///d:/Projects/EchoQ-Ops/ops/db.py#L131-L153)），这点已经是对的；缺的是**趋势**和**异常判断**。

### 3.4 内容复用（明确不学）

- CreatorHub 支持把已下载的抖音作品转发到小红书/视频号，把小红书作品转发到抖音。
- 这是“搬运”能力，和我们的原创定位、合规红线冲突，不做。

### 4.3 缺口

1. **发布结果没有“待确认”**：中断、超时、无回执时状态不准确。
2. **队列不可解释**：没有持久化的受阻原因、下次可执行时间、冷却状态。
3. **账号没有环境视图**：看不到登录态、出口、最近失败、当前风控状态。
4. **作品没有健康监控**：零播放、违规、下架、同步连续失败都不告警。
5. **指标没有历史**：只有当前快照，看不到趋势。
6. **没有通知渠道**：异常只能靠用户自己开面板看。
7. **没有 Profile 隔离与出口校验**：多账号并行时稳定性不足。
8. **没有账号分组/标签/批量操作**：号多了以后管理成本高。
9. **没有应用内备份/恢复**：换机、迁移靠手工拷目录。

## 6. 建议学习清单

### 阶段一：让发布后“看得懂”（优先）

**目标**：不增加新平台、不引入新依赖，把现有链路的状态说清楚。

1. **发布结果三态化**
   - `success / failed / pending_confirm`，中断、超时、缺少回执进入 `pending_confirm`。
   - `pending_confirm` 禁止自动重试，页面提供“去平台核对”和“确认已发布 / 确认未发布”两个动作。
   - 验收：模拟发布中断后，任务不会自动重发；人工确认后状态与平台一致。

2. **队列受阻原因持久化**
   - 记录 `blocked_reason`（限额 / 间隔 / 账号失效 / 冷却 / 平台规格 / 待确认）与 `next_run_at`。
   - 队列页直接展示“为什么还没发、什么时候能发”，不用翻日志。
   - 验收：任意等待中的任务都能看到一句中文原因和预计时间。

3. **账号详情一屏诊断**
   - 登录态、平台、最近巡检、最近发布、失败原因、当日已发/限额、同步状态。
   - 验收：账号异常时，用户在一个抽屉里能判断“重新登录 / 等限额 / 换号”。

4. **作品健康站内提醒**
   - 对已同步作品做规则判断：零播放、连续同步失败、指标骤降、平台返回异常。
   - 先在“内容库 / 概览”出站内提醒，不做站外通知。
   - 验收：构造零播放与同步失败数据，能在首页看到提醒并跳转到对应作品。

### 阶段二：让账号“管得住”

5. **每账号独立浏览器 Profile**
   - 在现有 `storage_state` 基础上增加持久 Profile 目录，带跨进程占用保护。
   - 验收：同一账号不能被两个任务同时打开；重启后登录态不丢。

6. **简化版代理池与出口记录**
   - 代理条目 CRUD + 测试（记录出口 IP、国家、时区）+ 账号绑定 + 出口变更提示。
   - 暂不做 ASN、指纹、出口组熔断。
   - 验收：代理失败明确报错，不静默直连；出口变化时账号详情有提示。

7. **统一写预算与冷却**
   - 同账号的发布、同步、登录检查共享写间隔；命中风控错误进入阶梯冷却。
   - 冷却结束先做轻量探测，恢复后逐级放开。
   - 验收：连续触发 429 后，任务进入冷却且不会被手动“立即执行”绕过。

8. **账号分组 / 标签 / 批量操作**
   - 按平台、用途、状态分组，支持批量启停、批量巡检。
   - 验收：20 个账号可在一次操作内完成分组与巡检。

### 阶段三：让作品“有价值”

9. **指标历史与趋势**
   - 新增按日快照表，保留 30/90 天趋势；当前表只留最新值。
   - 验收：单篇作品可看 7 日浏览/互动趋势，平台缺数据时断点而不是补 0。

10. **通知渠道（先站内 + Webhook）**
    - 事件：发布失败、待确认、账号失效、作品异常、同步连续失败。
    - 先做站内消息中心 + 通用 Webhook，后续再评估邮件/IM。
    - 验收：事件产生后 1 分钟内可在站内看到，Webhook 可收到。

11. **应用内备份 / 恢复**
    - 明确包含数据库、配图、Profile；密钥是否包含单独勾选；备份文件加密。
    - 验收：换机导入后可登录、可看到历史草稿与作品。

12. **评论只读监控（可选）**
    - 范围：小红书笔记评论、抖音短视频评论；公众号仅读取文章页公开可见的精选留言。
    - 严格只读：不回复、不点赞、不删除；手动同步优先，定时低频（6–24 小时）。
    - 两种用途：自己作品的反馈与风险发现；竞品/爆款评论反哺选题池。
    - 验收：同一作品重复同步不产生重复评论；评论为空时显示“平台未展示评论”而不是 0；公众号标注“仅精选留言，非全量”。

### 明确不做

- 快手 / 视频号 / TikTok 平台接入（当前阶段）。
- 私信、自动回复、自动评论、评论回复/点赞、关注/取关等互动能力。
- 搬运、去水印下载、跨平台转发已下载内容。
- 指纹浏览器与复杂反检测。
- 弹幕监控（仅抖音短视频，与图文为主的定位不匹配）。

## 7. 落地设计草案（文档级，不含代码）

### 7.1 数据模型建议

`accounts` 增补：

| 字段 | 用途 |
| --- | --- |
| `profile_key` | 独立浏览器 Profile 标识 |
| `proxy_group` | 出口组，空为 direct |
| `exit_ip` / `exit_checked_at` | 最近一次出口记录 |
| `health_state` | unknown / healthy / expired / risk |
| `cooldown_until` | 风控冷却截止 |
| `group_name` / `tags` | 分组与标签 |

## 8. 风险与注意事项

1. **不要照抄代码**：CreatorHub 仓库没有 License，代码不可合法复用；只学产品设计与交互。
2. **合规红线不变**：自动评论、私信自动回复、搬运下载都会放大平台规则风险，与我们的原创定位冲突。
3. **代理与 Profile 会提高复杂度**：先把“单机多账号稳定”做好，再考虑代理池；不要一开始就上指纹浏览器。
4. **待确认状态必须人工闭环**：任何“自动重试待确认任务”的设计都会导致重复发布，必须禁止。
5. **备份包含敏感信息**：Profile、Cookie、数据库、密钥的备份必须加密并明确提示，不能默认明文。
6. **指标缺失不等于 0**：延续现有 NULL 语义，趋势图断点而不是补零。
7. **评论只读监控必须严格只读**：不做回复、点赞、删除；公众号只能拿到精选留言，产品文案不能承诺全量。

## 9. 建议的推进顺序

| 顺序 | 事项 | 依赖 | 产出 |
| --- | --- | --- | --- |
| 1 | 发布结果三态 + 人工确认 | 无 | 队列/记录状态准确 |
| 2 | 队列受阻原因 + 账号诊断 | 1 | 用户自助排障 |
| 3 | 作品健康站内提醒 | 2 | 发布后闭环 |
| 4 | 独立 Profile + 简化代理测试 | 2 | 多账号稳定 |
| 5 | 统一写预算与冷却 | 4 | 降低批量失效 |
| 6 | 指标历史 + 通知中心 | 3 | 数据资产化 |
| 7 | 备份/恢复 | 4 | 可迁移 |
| 8 | 评论只读监控 | 3 | 反馈与选题反哺 |

每阶段完成后再评估是否继续，不一次性铺开。

## 10. 验收口径

一个改动算完成，至少要满足：

- 用户能在界面上回答“为什么没发出去 / 发出去后怎么样 / 这个号还能不能用”。
- 任何异常都有中文原因，技术细节只进日志。
- 待确认任务不会被自动重试。
- 平台没返回的指标不被写成 0。
- 评论重复同步不重复入库；公众号评论标注“仅精选留言”。
- 新增能力不改变现有平台适配器接口，不引入外部 CDN。
- 自检项同步更新，`python -m ops selfcheck` 全绿。
